用 Claude Code 重建我的博客:从 WordPress 到 Next.js 全栈单体

诸葛东明 · 2026-09-28 · 12,408 · ≈ 28 min
https://17aitech.com/%E7%94%A8claude-code%E9%87%8D%E5%BB%BA%E6%88%91%E7%9A%84%E5%8D%9A%E5%AE%A2/ 复制

154 篇文章、296 个用户、3314 篇弃用资讯——这是旧 WordPress 站的全部家当。这篇文章记录我用 Claude Code 把它重建成 Next.js 15 全栈单体的完整过程:哪些东西必须原样保留,哪些果断弃用,以及一路踩过的坑。

SEO 是这个站的生命线。旧文章 URL(中文 percent-encoded slug)必须一个字符都不变地继续可用——这是整个迁移的第一红线。

为什么是 Next.js 全栈单体

备选方案有三个:纯静态生成、Headless CMS + 前端、Next.js 全栈单体。最终选择全栈单体的理由:

  • App Router RSC/ISR:前台静态化,后台动态渲染,一个应用全覆盖
  • Prisma/PostgreSQL:154 篇文章的引用关系、媒体闭包需要真正的关系型查询
  • Redis/BullMQ worker:图片转码、统计聚合这些慢活,不能堵住请求

一个人 + 智能体军团的运维能力边界,单体是最优解。部署形态是单镜像双角色(web / worker 同镜像不同启动命令)。

迁移红线:URL 一个都不许变

旧站的 slug 是中文,入库后被 percent-encode。新站所有含 slug 的路由/查询必须经过同一个 normalizeSlug 实现:

 TypeScript · src/lib/slug.ts
// 编码 ↔ 解码往返,二次编码、% 字面量、+/空格 全边界单测钉死
export function normalizeSlug(raw: string): string {
  // 先解码一次,再走规范化,禁止直接拿 params 查库
  const decoded = safeDecode(raw)
  return decoded.trim().toLowerCase()
}

配套的迁移守卫跑在 CI 里:每次 PR 从零重放全部迁移,migrate diff --exit-code 断言实际库与 schema 一致。

哪些被果断弃用

3314 篇爬虫资讯——低质内容拖累 SEO,全部 301 到 /articles 承接旧链路。这个决定让迁移工作量少了三分之二。

Claude Code 在其中的角色

整个项目是我一个人 + Claude Code 完成的。工作流是:我出决策,智能体出实现。文档体系(requirement/arch/standard/plan)是人和智能体的共同上下文——CLAUDE.md 是智能体每次会话的入口,架构文档按需加载。

环节人负责智能体负责
架构决策定方向、拍板出方案、列权衡
编码实现Review 把关写代码、跑测试
数据迁移验收标准脚本 + 对账全流程

小结

重建不是重写。154 篇文章的历史 URL、296 个老用户的登录习惯、每一张引用图片,这些「旧资产」才是迁移的真正主体。新技术栈只是壳,资产无损才是里。
